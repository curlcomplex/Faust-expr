## Why Juno106 needed code rather than another preset

The dry A47 capture has a periodically rising/falling resonant ridge. A prior
v1 preset-only fit reduced aggregate error but missed this audible motion; it is
not the final revised study. Roland's historical hardware specification lists
both VCF LFO modulation and VCA ENV/GATE selection:
https://support.roland.com/hc/en-us/articles/201966419-Juno-106-Technical-Specifications

v3 retains v1's voice/VCF path and adds those dimensions with neutral defaults.
The fitted filter LFO is approximately0.3855Hz and1.675octave peak depth. Phase is
a laboratory capture-alignment control, not a claimed physical panel knob. It
runs continuously rather than restarting for each note. The triangle/depth law,
0.5ms gate-edge slew and per-instance modulation are model hypotheses; hardware
polyphony/global-LFO behavior has not been qualified. Canonical one-note
`gate` / `freq` in Hz / `velocity`, host polyphony, external chorus remain intact.

Removing only VCF modulation worsens training spectral error from3.63dB to8.01dB.
Gate mode is not superior on every metric: ENV mode slightly improves the later
combined/envelope loss while worsening the spectral component. Do not overstate
that ablation as proof of the original physical VCA setting. Quiet release tails
still differ. The clear supported correction is the missing VCF motion.

## Measurement and evidence boundaries

Search used native C++ generated by actual Faust, called by a thin adapter over
this repository's renderer. Its output was checked against the canonical offline
runner at blocks1,127,512, maximum sample error0 for each delivered study. Python
extracts features and proposes controls; it does not synthesize the instrument.
The fitting objective combines logarithmic RMS-envelope and multiresolution
log-band spectral residuals. These are diagnostic dB errors, not realism scores.

Juno-60 and SH101 fit early notes and evaluate later notes. Juno106 fits0..2.56s;
5.30..6.80s is reserved temporal evaluation after development inspection of the
middle of the take. All windows are from the same recordings: this is not an
independent unit/patch/control hold-out. Inferred MIDI timing and pitch are
nuisance estimates, not original session data. Juno-60's publisher recording is
stereo and was downmixed for timbre analysis; unknown chorus/capture processing
prevents claiming dry component calibration or stereo matching.

Later-note spectral residuals, before to revised: Juno-60 15.17 to5.06dB;
SH101 13.27 to3.49dB; Juno106 12.42 to5.02dB. Numerical reductions do not grant
musical acceptance. No full instrument, panel law, multi-unit variation, device
performance or authoring integration is approved here.

## Reproduction / listening

With the repository's Faust/C++/NumPy/SciPy/SoundFile dependencies installed:

```sh
python3 tools/modules/hardware_listening_delivery.py --out build/hardware-delivery
```

This rebuilds the frozen sounds, validates source identities, renders both
versions from identical scores, checks retained raw RMS values and exports the
listening WAVs. It is not a fresh optimization or a claim to revalidate all
hardware descriptors. The preparation workflow pins original recordings and
exports reproducible analysis descriptors. Search code/reports and byte hashes
are also supplied in the session's study bundle.

The Juno106 author explicitly permits distribution; the original notes travel
with its excerpt. Juno60 and SH101 publisher audio is not repackaged: use the
original MP3 links beside the local before/revised players. This preserves an
actual hardware A/B without silently relabeling synthetic audio as a reference.
Mini dropout tests and owner-rejected PR89 audio are engineering/rejection
records, not part of this musical listening package. Draft/unmerged, no factory
selection or saved-project migration.
