# Upstream Faust loop-split/fusion result

Date: 2026-09-08

This records a focused evaluation of recent upstream Faust `ocpp` loop-split/fusion work before Curlop invents any new partitioner or scheduler.

## Scope

Pinned Faust commit: `3d4baa164c0dd31b7d147617ed84a626495148dd` (2.88.0-era tree).

Test DSP: 32 independent oscillator voices, each followed by a deliberately heavy chain of low/high-pass filters, summed to stereo. This is the same broad workload family used to distinguish scheduler overhead from useful parallel DSP work.

The test uses Faust's `ocpp` backend and the official `faustcompilerbenchtool` wrappers. It does **not** establish LLVM/libfaust JIT support, bitcode caching, realtime suitability, or production correctness.

## Broad pass

Ordinary `ocpp` best: **31.2836 ms**.

Plain loop-split variants were consistently slower:

- `-ls -ls-sched df`: **41.749 ms**
- `-ls -ls-sched model`: **41.8578 ms**
- `-ls -ls-sched cs2`: **41.7355 ms**
- `-ls -ls-sched cs2b`: **41.8337 ms**

So materializing/scheduling the loop DAG without fusion is about one third slower than ordinary `ocpp` on this workload.

The first `-ls-fuse` attempt hit Faust's default 120-second compiler timeout.

## Focused fusion pass

The focused rerun raised Faust's explicit timeout to 600 seconds and measured two fusion schedules.

| Variant | Faust compile time | generated bytes | C++ `for` loops | best benchmark | speedup vs same-run `ocpp` |
|---|---:|---:|---:|---:|---:|
| `ocpp` | 1.102 s | 488,398 | 420 | 32.0919 ms | 1.00x |
| `-ls-fuse -ls-sched df` | 310.853 s | 474,257 | 928 | 19.0558 ms | **1.684x** |
| `-ls-fuse -ls-sched cs2` | 303.339 s | 474,263 | 928 | 17.7971 ms | **1.803x** |

The result is therefore not "loop splitting is faster". The useful result is much narrower:

> **Upstream's cost-guided loop-split fusion can substantially outperform ordinary `ocpp`, while plain loop splitting is substantially slower.**

This is directly relevant to Curlop because the upstream implementation addresses the same locality/fusion problem observed in stock `-sch`: same-loop producer/consumer reads can be scalarized back to producer root values rather than forced through materialized intermediate buffers. Its fusion logic also contains a cost model for loop/chunk overhead, register pressure/spills, buffer loads, and compile-time fused-op limits.

## Correctness screening

The official text impulse outputs are not bit-identical to ordinary `ocpp`.

All variants produced the same 44,100-frame stereo output length. Independent numeric comparison of the saved impulse responses gave approximately:

- `ls-fuse-df`: max absolute delta **1.297e-5**, RMS delta **3.065e-6**
- `ls-fuse-cs2`: max absolute delta **1.2963e-5**, RMS delta **3.001e-6**

Reference output RMS was approximately `7.1412e-3`, so the RMS delta is around **0.04% of reference RMS**. This is compatible with floating-point reassociation/reordering, but this experiment does not prove that interpretation. Do not relax a production correctness threshold post hoc; qualify the numerical contract separately.

## Interpretation for Curlop

This materially changes the research direction. We should **not** design a new coarse-region cost model from zero until we have evaluated reuse of this upstream machinery.

The highest-value reuse candidates are:

1. the upstream super-node/materialized-loop representation;
2. the legal fusion-candidate logic;
3. the shadow cost oracle used to decide whether a fusion is profitable;
4. same-loop producer/consumer scalarization that restores register/locality benefits;
5. the upstream scheduling variants as candidate intra-region orders.

However, this code currently lives in the experimental `ocpp` path. Curlop's desired desktop runtime is libfaust LLVM + cached bitcode, so direct product adoption is not yet demonstrated.

The next narrow research question is therefore **not** "can fusion help?" — this test says yes. It is:

> Can the upstream loop-split/fusion plan be exposed or reused before backend emission so that the same profitable regions can be emitted/compiled through Curlop's LLVM/JIT path, or must we choose between an AOT-C++ derived build and porting this pass into the LLVM lowering path?

That question should be answered before writing a Curlop-specific partitioner.
