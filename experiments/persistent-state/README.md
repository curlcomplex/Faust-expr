# Persistent state across editable and optimized execution

This is a gated engine experiment extending the existing public native environment, not an enabled product path. The user approved investigating optimized A -> immediately edited B -> optimized B while keeping compatible running state and the unified-Faust performance benefit.

## What this candidate actually is

Faust's stock `-os -ec` C++ backend generates each unchanged module's state object, control routine and per-sample routine. Their exact generated declarations are shared by every graph-specific kernel. A native Bank owns those objects independently of graph-code lifetime. The editable path calls block loops on those same objects; the optimized path has one statically composed sample loop with every Faust-generated sample routine visible to Clang/LLVM inlining and optimization. No generated field names are guessed, no raw struct copies, no reconstructed delay history and no hand-rewritten DSP. A compiler/schema fingerprint checks exact module identities, source, generated headers, compiler and options. Both code versions borrow the same state, sequentially, never concurrently.

This is **not** a new stock libfaust whole-graph state-relocation API. Faust front-end algebraic fusion across modules can differ from this LLVM-level inlining. That is why the first gate compares against a full ordinary Faust/LLVM program as well as full generated C++, with identical taps, input mix planes and a common peak/RMS observer. It measures bare DSP separately so common observer cost cannot conceal a large kernel regression. Actual unchanged product-renderer named taps qualify the graph semantics. The accepted BEN-008 source/effect family is included; no new APG baseline is invented.

The capability probes demonstrate the actual installed backend restrictions. External-memory flags require -it; -mem3 additionally requires C and -ec. The installed LLVM backend rejects these modes. This candidate instead retains complete compiler-generated module objects and uses the public one-sample interface; no compiler source fork is necessary. The state scope is unchanged authored modules during topology changes, not arbitrary source or compiler-layout migration.

## Gates declared before native results

1. Nine graph families/sizes, at64/128 frames plus512 forBEN64, compare stock whole Faust LLVM, stock whole C++, optimized shared-state kernel and editable shared-state execution. Source/effect code comes from the existing native fixtures plus the accepted BEN-008 constants. Master/node-tap equivalence is checked against the real product builder. Full waveforms are retained. Each arm has the same common observer workload. Eleven shuffled256-block timing batches measure both bare DSP and DSP+observers. Engineering screen: geometric-mean optimized/shared time vs whole-LLVM <=1.25 bare and <=1.20 observed; no individual bare ratio >1.75. These are prototype screening bounds, not a user-perceptual or production SLA.
2. Only after the first gate is positive: optimizedA -> editableB -> optimizedB -> editableA -> optimizedA, with previously absent routes, irregular positive blocks, sample-offset gain changes and a long-delay memory fixture. The independent continuing reference uses separately compiled stock LLVM modules, not the candidate's generated state routines. Precompiled optimized versions make this a state-continuity gate, **not proof of online compile/publication time**.
3. Positive transition evidence permits a subsequent actual background-compilation/publication stress test. It is not included implicitly by passing the preceding gate.

Absolute+relative sample bound:1e-5+1e-5*abs(reference), unchanged from previous cross-backend experiments. No gain fit, normalization or time alignment. Negative reset recordings remain. Callback-size partition and actual audio-device guarantees require their own evidence. Initial state/table allocation is outside compute; a whole bank exists before the edit. No claim of arbitrary new modules, full CV/MIDI/polyphony, lock-free production retirement or multicore.

Generated headers, source, LLVM IR, native libraries, manifests, source and binary hashes, raw captures and failed logs are retained. Library ownership outlives every borrowed state/kernel. Production source, existing experiments and main/master are untouched.
